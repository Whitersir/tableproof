# 你可以独立完成的三个小任务

按顺序做即可。每次先预测结果，再改动，再运行检查。暂时不用同时理解全部文件。

## 任务一：让自己的两张表跑起来（约 30—60 分钟）

1. 复制 `samples` 中两个文件，使用虚构姓名，新增一个学号为 `007` 的报名人，先不签到。
2. 预测有效报名、到场、未到场和到场率。
3. 在网页上传副本并核对。预期是 7、4、3、57.14%。
4. 再把 `007` 加入签到表，重新上传两张表。预期是 7、5、2、71.43%。
5. 下载明细，找到 `007` 的报名和签到源记录号。

完成后你应该能解释：表里有多少行，为什么不一定等于有效人数；文件变化后为什么要重新导入。

## 任务二：给统计增加一个指标（约 1—2 小时）

目标：在 `app/reconcile.py` 的 `totals` 中增加 `absence_rate`，表示未到场率。

提示：用现有 `percentage()`，不要让模型计算。有效报名为零时仍应返回 `None`。

验收：

- 示例数据未到场率为 `33.33`。
- 无有效报名时为 `None`。
- 在 `tests/test_business.py` 增加自己的边界用例；示例的完整字典断言也需补上新字段。
- 可先通过 `/docs` 或测试观察接口值，再考虑加到网页，不必一次修改所有层。

完成后你应该能解释：为什么使用 Decimal，为什么不能把 `100 - 已四舍五入的到场率` 当成唯一实现。

## 任务三：独立完成一个字段映射与失败修复（约 1—2 小时）

1. 把签到副本的“学生编号”改成“学员编号”。
2. 用网页手动选择正确字段并成功核对。
3. 找到 `web/app.js` 中 `idAliases` 数组，把新别名加入。
4. 再导入，确认主要字段能自动建议为“学员编号”。
5. 在 API 测试中新增相应表头用例，确保后端本来就不依赖固定中文列名。

完成后你应该能解释：前端建议和后端规则的区别，以及模型可能在哪一层选错字段。

## 简短记录模板

每做完一个任务，保留四行即可：

```text
我修改了：
我预计会发生：
实际检查结果：
我现在能独立解释或修改：
```

当你能解释本地流程后，再读 `agent.py` 的 while 循环、`needs_review` 状态，以及 `settings.py` 的配置流程。你可以在页面配置自己的中转站；先核实接口和工具调用支持，再用虚构数据跑一条真实任务。你不需要先掌握整个前端生态。
