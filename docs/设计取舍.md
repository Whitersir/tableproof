# 设计取舍

## 先有普通程序，再开放模型工具

CSV 读取、身份匹配和统计没有必要依赖大模型。先把确定性业务函数独立出来，再将它们包装成工具，能够使用固定答案检查计算，也便于比较本地表单与自然语言入口的收益。

Agent 的价值需要通过真实任务验证。本项目没有宣称自然语言入口总比表单快；对于重复固定流程，本地方式更直接。

## 执行前展示方案

模型选出一个合法字段，并不代表选对了用户想要的字段。比如把“只看一班”理解为全表核对，计算可能完全正确，但任务仍然失败。

因此新增 needs_review 状态：工具首次提交参数，程序验证字段与规则后展示；用户确认后，模型必须以相同参数再次调用才执行。更改匹配或筛选口径会重新要求审阅。这样把“意图是否正确”与“计算是否正确”分开检查。

代价是多一次用户操作和可能增加模型调用轮次。这适合首次核对和不熟悉数据的情况；未来可在真实评测后考虑用户保存常用方案。

## 不开放任意代码执行

允许模型自由生成 pandas 代码会扩大分析范围，但也引入代码隔离、文件访问和资源限制等额外工程问题。当前只提供有类型约束的工具，任务范围保持在 CSV 报名签到核对。

## 不把模型文本当作报告数字

统计数字来自 reconcile.py；报告来自 reports.py。模型的自然语言解释不会覆盖结果。这样避免“工具算对了，模型又在总结时改错数字”的第二条出错路径。

## BYOK 与本机设置

密钥由用户自己的浏览器发到本机 Python 服务，由后端请求供应商。页面查询只返回是否已有密钥；保存后输入框清空，不使用浏览器持久存储。

本机 JSON 文件是容易理解的初期方案，未声称加密保险箱。若未来部署为多人服务，需要重新设计认证、密钥托管、租户隔离与操作审计，不能直接把当前服务开放到公网。

## 为什么不用前端框架与编排框架

当前界面只需要文件上传、字段配置、表格和任务状态。原生 JavaScript 已覆盖需求；Agent 循环也足够短，可以直接观察消息、工具执行和状态转换。引入框架应由规模或维护需求触发，而不是为增加技术名词。

## 哪些证据能证明什么

- 单元测试：给定输入下，业务与控制逻辑符合预设行为。
- 模拟 HTTP 集成：浏览器、后端、工具协议与方案审阅能够贯通。
- 真实模型评测：模型能否理解任务并提出正确参数，当前待完成。
- 实际用户试用：是否比现有操作更省事，当前待完成。

这四类证据不能相互替代。
